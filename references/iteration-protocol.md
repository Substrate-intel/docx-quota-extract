# 迭代协议：skill 自我迭代 + 版本管理 + 跨用户回流（v1.1 定版）

> 目标：每一次用本 skill 完成一卷提取，skill 本身必须变得更好；
> 任何使用者（含跨用户）的迭代都能以受控质量回流，而不是只在本地各自漂移。

## 一、强制回写清单（每卷门控全绿收官后执行，属于收官动作的一部分）

完成一卷后，**必须**按以下顺序回写 skill（禁止"用完就走"）：

| # | 回写对象 | 触发条件 | 动作 |
|---|---|---|---|
| 1 | `references/pitfalls.md` | 本卷踩了新坑（SKILL/pitfalls 已有清单之外的形态） | 追加新坑：**症状→根因→根治→验证证据**四件套，编号续接（`坑 21` 起） |
| 2 | `references/volume_params.md` | 本卷参数替换中发现新的硬编码形态 | 追加到替换点地图；若属通用形态，同步追加 `check_volume_params.py` 的 CHECKS 项 |
| 3 | `references/pipeline.md` | 出现阶段级差异（新阶段/验收口径变化/新记录形态） | 更新对应阶段；注明变更来源卷 |
| 4 | `scripts/check_volume_params.py` | 发现新的"漏改会静默错配"特征 | 追加 CHECKS 模式（用本卷实测值验证过再入） |
| 5 | `scripts/*.py` | 本卷产生可复用的结构性改进（非卷特有逻辑） | 回写参考实现；卷特有逻辑只入 pitfalls/params 文档，**禁入通用脚本**（防卷耦合污染） |
| 6 | `CHANGELOG.md` | 上述任一回写发生 | bump 版本 + 记录（见下） |

### 回写完成动作（回流两连，v1.2.1 起强制——禁"回写完成但停留工作区"）

sz01 v1.2.0 曾实证踩过断点：回写完成、commit/push 却没做，用户查问才发现未回流。
自 v1.2.1 起回写清单执行完毕后**必须**机械回流（不再依赖人工记得推）：

1. **skill 仓回流**：`python scripts/sync_skill_remote.py --tag vX.Y.Z -m "<卷名>回写 vX.Y.Z"`（dirty 检测→commit→打 tag→push，幂等；工作区干净时只补推）；
2. **成果仓回流**：`python <项目根>/sync_remote.py`（各卷 db/前端/交付报告/门控基线 → `ln2024-quota-volumes` 私有仓，幂等 up-to-date 即止）。

成果仓铁律：源文件（input/ 官方 PDF、docx 源）**永不回流**（版权+体积）；中间产物
（out/*.json 过程态、取证 jpg）不回流（基线指纹已锚定可复现）。脚本自动发现新卷，
新卷零维护。

## 二、迭代质量门槛（三件准入制，禁止只记症状）

一个新坑/新检查项要回写进 skill，必须同时具备：

1. **根因**：说清为什么会发生（结构层根因，不是表象复述）；
2. **根治**：给出可复用的修法（代码要点/正则/守卫），且**不能是"下次注意"式的口头纪律**——
   凡可通过机械手段防住的（扫描器检查项、断言、门控），必须落成机械手段；
3. **验证证据**：本卷已跑过门控/复现验证的记录（数字口径，如"门9 175/175 全等、cell_diff=0"）。
   未经本卷验证的只能写入"待验证"状态并注明。

**禁止入清单**：只在本卷出现一次且无复用可能的卷特有细节；带敏感路径/个人信息的内容。

## 三、版本管理（git + 语义化版本 + tag）

- skill 目录即 git 仓库：`~/.workbuddy/skills/docx-quota-extract/`；
- 版本号 `vMAJOR.MINOR.PATCH`：
  - **PATCH**（v1.1.0→v1.1.1）：文档修订、错别字、pitfalls 补充不改结构；
  - **MINOR**（v1.1→v1.2）：新增检查项、新坑入库、脚本兼容性改进（向后兼容）；
  - **MAJOR**（v1→v2）：管线阶段结构变化、脚本接口不兼容变更；
- 每次回写：`git commit`（消息格式 `MINOR: +坑21 目录行页码粘连（sz10卷）`）→ `git tag v1.x.y`；
- 打包件命名同步：`docx-quota-extract-v1.x.y.zip`。

## 四、跨用户回流协议（使用者的迭代如何回到作者处）

**分发形态**：zip 包（`package_skill.py` 产物）或 git 仓库（建议托管 GitHub/Gitee）。

**使用者迭代流程**：
1. 解包/clone skill → 使用（正常完成一卷）；
2. 按「强制回写清单」迭代 → bump 版本 + CHANGELOG 记录；
3. CHANGELOG 每条**必须含来源标识**：`- 来源: <使用者标识/卷名> · <联系方式或仓库>`；
4. 回流二选一：
   - **git 路径**（推荐）：fork 仓库 → 提交迭代 → 发 PR/MR（diff 清晰可审）；
   - **zip 路径**：重新打包发回作者（附 CHANGELOG diff）。

**作者审核门槛**（合并前必查）：
- [ ] 每条变更过了"三件准入制"（根因+根治+证据）？
- [ ] 卷特有逻辑没有混进通用脚本？（抽查 scripts/ diff）
- [ ] 新 CHECKS 项验证过不误伤通用代码？
- [ ] 版本号 bump 符合语义化规则？
- 未过审的变更：打回并注明缺哪件；过审 → 合并 → tag → 发新版包。

**冲突处理**：多来源同坑不同解 → 保留更机械化的根治（可验证优先于口头纪律），两案并记 pitfalls 注明取舍。

## 五、防漂移守卫（为什么这套协议能防"各自漂移"）

- skill 内脚本带 sz05 基准值 + 扫描器比对 → 使用者改没改、改得干不干净，**机械可验**；
- 版本号 + CHANGELOG → 任何一份 skill 的演进历史**可追溯**；
- 回流必须带证据 → 迭代质量**有门槛**；
- 作者审核 checklist → 合并权收敛，**不会出现两个互相不认识的"官方版"**。
